## Surprises & Discoveries

Found while verifying this plan against the code (2026-09-24):

- **Backend has newer tags than production.** `v0.11.10` and `v0.11.11` exist (#830–#839: `target_release_id`, OS fields on schemas, release semver sorting, archiving tweaks). None of them touch the device services, device views, device permissions, or the frontend API spec that this plan cites (`git diff --stat v0.11.9 v0.11.11` on those paths shows only `internal/configs/ugc` filepath helpers). If production has moved past `v0.11.9` by the time you execute, re-run the greps for each issue against the new tag.
- **Saved views are open to every role.** The viewer role grants create, update and delete on device views (`internal/authz/permissions/configs/role_grants.go`, `viewerGrants`). Private views are visible only to their creator (`internal/configs/db/security.go`, `shared = true OR created_by = user`). So anyone who can see a shared view can edit or delete it.
- **View names are unique per person, not per workspace.** The unique indexes are `(name, workspace_id, created_by)` for workspace views and `(name, group_id, workspace_id, created_by)` for group views (`tools/supabase/migrations/20260907120000_add_device_views.sql`). A group's views are deleted with the group (`ON DELETE CASCADE`).
- **A view needs a filter.** The frontend disables **Save** with the tooltip "Add a filter to save a view" until there's at least one search term or filter (`hasDeviceViewFilters`). Display-only changes can't be saved as a new view.
- **The list has built-in Active and Archived tabs.** Saved views are tabs after them (`src/components/lists/components/ListViewTabs.tsx`). Archiving is out of scope, so how to mention the Archived tab is asked at ENG-1386.
- **Where list settings are stored.** Search, filters, grouping and ordering are URL query params (`useDeviceFilterParams.ts`, nuqs). Multi-select, compact rows and (outside a saved view) column visibility are per-browser cookies (`utils/preferences.ts`). Inside a saved view, hidden columns are part of the view.
- **The reprovision gate is reported by the backend, not enforced by it.** *(Corrected at ENG-1387.)* Besides the frontend's `REPROVISION_MIN_AGENT_VERSION = '0.9.0'`, the backend's action resolver marks reprovision invalid below v0.9.0: "Device must be running agent v0.9.0 or later to be reprovisioned" (`internal/authz/actions/device.go`, `resolveReprovision`). That only feeds `device.actions.reprovision`, which the dashboard reads. Creating a `reprovision` provisioning token (`services/provisioning_tokens/create.go`) and the reprovision itself (`services/devices/reprovision.go`) don't check the device's prior agent version. The docs are still right, because reprovisioning is dashboard-only.
- **The Activity timeline only shows deployments that reached the device.** It lists deployments with target status `deployed` or `archived` that were queued, newest first (`src/features/deployments/utils/search.ts`, `DEVICE_DEPLOYMENT_FILTER`). Staged deployments aren't in it.
- **The device name limit wasn't re-verified.** `overview.mdx` says names are 1–48 characters. That rule lives in `github.com/mirurobotics/core` (`ugc.SanitizeName`, v0.10.4), which isn't checked out locally. M2 doesn't change that sentence.

Found while executing (2026-09-24 and 25). Prod stayed at frontend `2b3ffed6` and backend `v0.11.9` (`80acefec`) throughout; the backend's vendored frontend spec pins openapi `3e881e4c` (API `v0.9.4`), which matches the production build info Armel shared.

- **Clicking a device doesn't always open the last-used tab.** An active device with no release opens the **Editor** tab, with the Set release dialog if you can deploy (`useDevicesList.ts`, `handleClick`). The docs don't describe tabs at all anymore (ENG-1384 decision), so nothing depends on it.
- **Inline description editing isn't permission-gated.** The Overview's description textarea never checks `device.actions.update.allowed`; a viewer only learns they can't edit from the error toast. Filed as [ENG-1417](https://linear.app/mirurobotics/issue/ENG-1417) (M9).
- **Bulk archive is capped at 100 in the backend only.** `MaxBulkArchiveDevices = 100` (`services/devices/errors.go`, checked in `bulk_archive.go`), but the frontend never disables **Archive** over 100 and the spec's `BulkArchiveDevicesRequest` has no `maxItems`. Bulk move's 1,000 cap is in all three places. Filed as [ENG-1418](https://linear.app/mirurobotics/issue/ENG-1418) (M9). The docs state the 100 limit.
- **Group managers can move devices.** `Devices.Move` is granted only by the group manager role (`role_grants.go`, `groupManagerGrants`), plus admins. `concepts/devices/manage.mdx` showed only `<AdminBadge />` on "Move a device"; `concepts/groups/manage.mdx` already had both. Fixed at ENG-1385.
- **Duplicate opens the view editor, it doesn't copy.** It pre-fills "*name* copy" with the original's settings, and you still click **Save** (`useDeviceSavedView.ts`, `duplicate`).
- **Anyone can unshare someone else's shared view.** `services/device_views/update.go` accepts `shared` with no creator check. The view then becomes private to its original creator and disappears for the person who changed it. Not documented, not filed.
- **The platform API can't search device descriptions.** `listDevices` has `device_search_name` but no description search (`2026-08-17.yaml`). The Search section's API badge stays; name search is supported.
- **`provisioning/reprovision-dialog.png` is outdated, contrary to this plan.** It shows the command without `sudo` or `systemctl stop`/`start`; prod builds `sudo systemctl stop miru` / `sudo -u miru MIRU_PROVISIONING_TOKEN=… /usr/sbin/miru-agent reprovision` / `sudo systemctl start miru` (`provision/utils/token.ts`), which the command breakdown below it already describes. Armel deferred image changes on that page.
- **A GET on a not-yet-uploaded CDN URL caches a 404 for 4 hours.** Checking whether a name was free with `curl -o /dev/null` warmed Cloudflare's edge with a 404 (`cache-control: max-age=14400`), so the image stayed broken after upload until Armel purged it. Check names with `curl -I` (HEAD) only.
- **Screenshots pasted into chat are downscaled JPEGs.** Saving the chat copy gave a 1024-px JPEG in a `.png` file. Use the original from the Desktop.
- **Edits can race with the IDE.** One `StrReplace` reported success while the open editor saved over it. Re-read the file after editing a file Armel has open.

### Previewing (lessons from M1)

- **Hard refresh after every edit** with Cmd+Shift+R. A tab that lost its live-reload connection keeps showing the old page even though the server has the change.
- **Restart the dev server after editing `docs.json` or anything in `docs/snippets/`.** Mintlify doesn't hot-reload those reliably. ENG-1382 (a snippet) and ENG-1385/ENG-1386 (new nav entries in `docs.json`) need this. In the terminal running the server, press Ctrl+C, then:

        cd ~/dev/miru/docs && pnpm dev

- **Replaced screenshots can look stale.** `assets.mirurobotics.com` sends no `Cache-Control` header, so browsers may keep an old image at the same URL for days. That's why Armel uploads replacements under a new name.

### Checks for every issue

Run from the repo root:

    ./scripts/lint.sh     # last line must be: All documentation lint checks passed.
    pnpm validate         # must end with: success build validation passed

`lint.sh` runs the custom Go MDX linter (sentence-case headings, no `--`, import and redirect rules), ESLint on MDX, CSpell (`cspell.json`), and the OpenAPI checks. If CSpell flags a real word, add it to `words` in `cspell.json` and include that file in the commit. `pnpm validate` doesn't catch links to non-page paths, so open every link you write on localhost.

## Idempotence and Recovery

- Every edit is a text insertion or replacement, or a new file. Before reapplying, check whether the new text is already there (`grep`) and skip it if so.
- Before a commit, `git restore <file>` undoes an edit, `git restore --staged <file>` unstages, and a new page can be removed with `rm` (it's untracked).
- To change an earlier issue's commit after later ones exist: `git commit --fixup <sha>` then `git rebase -i --autosquash origin/main`. That's safe because nothing is pushed. Never force-push.
- The frontend and backend repos are read-only. `git -C ~/dev/miru/frontend status --short` and `git -C ~/dev/miru/backend status --short` must stay empty, and neither checkout's branch changes.
