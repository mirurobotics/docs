## Purpose / Big Picture

The groups docs still describe the old Groups page: a table with **+ Group** in the top right, an **Edit** action, moving groups through the API only, and a **Members** dialog. The Sep 23 release rebuilt the page as three resizable panes:

- a **tree** of groups, where groups are created and managed;
- the selected group's **devices**, using the same list as the Devices page;
- a **details** pane with a Group card and a **Members** card.

After this milestone, `concepts/groups/manage.mdx` describes the three panes, creating groups and subgroups, **Rename**, **Move** in the app, and the group devices pane. `concepts/groups/members.mdx` describes the Members card and the Add members dialog. The device list itself isn't repeated; it links to the Device views page and Bulk actions that M2 shipped.

## Surprises & Discoveries

Found while re-verifying (2026-09-25):

- **Nothing moved since the audit.** Frontend `origin/prod` is still `2b3ffed6`. `git log --since=2026-09-23 origin/prod origin/main -- src/features/groups src/features/access 'src/app/(app)/groups' src/features/devices/components/list src/views/sidebar` shows only #89 (Sep 23, display menu labels), which predates the audit. `origin/main`'s only extra commit, #90, touches in-app docs links for releases, the editor and buckets.
- **The M2 plan wasn't moved to `plans/completed/`.** It was still `plans/active/20260924-m2-devices.md` on `main`. Armel had it moved in its own commit on this branch (`docs(plans): complete the m2 devices plan`).
- **A group's devices pane lists only devices assigned directly to it.** Devices in subgroups aren't included (`group_id` equality: backend `internal/configs/db/device.go`, `BuildSearchByGroupID`). The Group card's **Devices** count works the same way (`fetchGroupDeviceCount`).
- **Only admins create top-level groups or move a group to the top level.** Creating a top-level group checks a workspace-level `Groups.Create`, and moving with no parent checks an unscoped `Groups.Move` (`internal/authz/actions/workspace.go`; `internal/configs/services/groups/move.go`). Group managers only hold these scoped to their groups, so they can create subgroups and move groups within groups they manage.
- **Who the Members card lists.** Active users who are owners or admins, workspace operators or provisioners, or who have a role on the group or a parent group (`internal/configs/services/groups/members.go`, `searchMembersForGroup`). Add members offers everyone else who's active, for example workspace viewers and publishers.
- **Remove access only removes the group's own roles.** Roles from the workspace or a parent group are locked in the menu, with a tooltip: "Granted by their workspace role — change it in workspace member settings." or "Inherited from an ancestor group — change it on that group." (`frontend/src/features/access/utils/sources.ts`).
- **You can't change your own roles.** The role button is disabled with "You can't change your own roles" (`frontend/src/features/access/utils/policy.ts`).
- **Search and filters carry over between groups.** The Groups page keeps one unsaved working set, so filters you set in one group stay applied when you pick another (`GroupsPage.tsx`, `readWorkingSet`). Saved views are per group and are deleted with the group (M2 finding, `ON DELETE CASCADE`).
- **Frontend TECH_DEBT TD-170 is stale.** It says the group members dialog runs on a mocked API, but production calls the real endpoints (`frontend/src/features/access/api/repository.ts`). That's frontend-repo debt; nothing to do here.
- **Platform API coverage.** `getGroup`, `listGroups`, `createGroup`, `updateGroup` and `moveGroup` exist. There's no delete endpoint (`docs/references/platform-api/2026-08-17.yaml`). The existing badges stay: `groups/get`, `groups/create`, `groups/update` (now on Rename), `groups/move`, and `PlatformUnsupportedBadge` on Delete, Move a device and the member sections.
- **The Move dialog has no Top level option.** Clicking the selected group again clears it, and the footer then reads "Top level" (`useMoveGroupSelection.ts`, `onSelect`; `MoveFooter.tsx`). **Move** is gated only when a group is selected (`blocked = selectedGroup !== null && …`), so a group manager can submit a move to the top level and gets the backend's error (`move.go`, unscoped `CheckRule`). Candidate M9 bug, not filed.
- **Add members searches by name only.** The dialog's placeholder says "Search people by name or email...", but the frontend sends only `contains('name', …)` (`access/api/repository.ts:68`) and the backend matches `first_name || ' ' || last_name` (`orgs/db/user.go:94-105`). The dev mock also matches email, which hid it. Filed as [ENG-1426](https://linear.app/mirurobotics/issue/ENG-1426) (M9); Armel chose to keep name-only search and fix the placeholder. The docs say "search by name".
- **Panel rows are gated per assignment.** Each group row in the user access panel uses that assignment's own `actions.update` / `delete` (`useAssignment.ts:73-74`), so changing an inherited role on the parent needs permission on the parent. Not documented; the badges cover it.
- **Mintlify curls apostrophes in anchors.** "View a group's devices" rendered as `id="view-a-group’s-devices"`, so `#view-a-groups-devices` (the plan's slug) was broken; `members.mdx`'s "Edit a member's access" is `#edit-a-member’s-access`. The new section is "View devices in a group" (`#view-devices-in-a-group`) instead. Avoid apostrophes in headings that get linked.
- **No other page links to a section anchor on the groups pages** (`grep -rn "groups/manage#\|groups/members#" docs`), so renaming headings is safe.

## Idempotence and Recovery

- Every edit is a text insertion or replacement. Before reapplying, check whether the new text is already there (`grep`) and skip it if so.
- Before a commit, `git restore <file>` undoes an edit, and `git restore --staged <file>` unstages.
- To change an earlier issue's commit after later ones exist: `git commit --fixup <sha>` then `git rebase -i --autosquash origin/main`. That's safe because nothing is pushed. Never force-push.
- The frontend and backend repos are read-only. `git -C ~/dev/miru/frontend status --short` and `git -C ~/dev/miru/backend status --short` must stay empty, and neither checkout's branch changes.
