## Purpose / Big Picture

Every Platform API endpoint page in the docs renders an autogenerated cURL sample and an API playground. Today the required `Miru-Version` header renders as an unfilled placeholder, so a reader copying the sample gets a request that the API rejects:

    curl --request GET \
      --url https://api.mirurobotics.com/beta/config_instances/{config_instance_id} \
      --header 'Miru-Version: <miru-version>' \
      --header 'X-API-Key: <api-key>'

After this change, the header carries the correct value for whichever API version's pages the reader is on — `2026-08-17.everglades` on the `2026-08-17` pages, `2026-05-06.rainier` on the `2026-05-06` pages, `2026-03-09.tetons` on the `2026-03-09` pages — in both the playground field and the autogenerated code samples. A reader can copy the sample, substitute only their own API key, and get a request the API accepts.

The user-visible verification surface is <https://docs.mirurobotics.com/references/platform-api/2026-08-17/endpoints/config-instances/get>: the cURL block must read `--header 'Miru-Version: 2026-08-17.everglades'` instead of `--header 'Miru-Version: <miru-version>'`.

## Context and Orientation

### How Platform API reference pages are built

`docs/docs.json` is the Mintlify site configuration (JSON, validated against `https://mintlify.com/docs.json`). Its `navigation.products` array contains a product named `"Platform API Reference"` whose `dropdowns` array has one entry per API version. Each entry points at a checked-in OpenAPI spec:

    { "dropdown": "2026-08-17.everglades",
      "openapi": { "source": "references/platform-api/2026-08-17.yaml",
                   "directory": "references/platform-api/2026-08-17/endpoints" } }

The four specs are `docs/references/platform-api/{2025-10-21,2026-03-09,2026-05-06,2026-08-17}.yaml`. Mintlify generates one endpoint page per operation; each page shows an API playground plus autogenerated code samples (cURL and others). "Prefill" is Mintlify's term for seeding those with values taken from the spec instead of showing angle-bracket placeholders derived from the parameter name.

### The `Miru-Version` parameter already carries the right value

Verified 2026-09-02 by reading each spec. The three newer specs each define, under `components.parameters`:

    MiruVersion:
      name: Miru-Version
      in: header
      required: true
      schema:
        type: string
        example: 2026-08-17.everglades   # 2026-05-06.rainier / 2026-03-09.tetons in the others
      description: The API version the client was built against.

`docs/references/platform-api/2025-10-21.yaml` has no `Miru-Version` parameter at all — that version predates the header. It is untouched by this change and its pages will continue to render no version header.

So the correct value is already in the data. What is missing is the configuration flag that tells Mintlify to use it.

### `docs/docs.json` already has an `api` block

Contrary to a first reading, `docs/docs.json` does have a top-level `api` key. Its current value is:

    "api": {
      "params": { "expanded": "closed" },
      "playground": { "display": "simple" }
    }

There is no `examples` sub-object. This edit adds one.

### The Mintlify option, confirmed from the pinned toolchain

`package.json` pins `mint@4.2.842`. After `pnpm install --frozen-lockfile`, the docs.json schema is defined in Zod at:

`node_modules/.pnpm/@mintlify+validation@0.1.842_*/node_modules/@mintlify/validation/dist/mint-config/schemas/v2/properties/api.js`

That file defines `api.examples` with four optional keys, quoting its own `.describe()` text:

- `defaults`: `'required' | 'all'` — "Whether to show only required parameters in the examples, defaults to `all`."
- `languages`: array of strings — "Example languages for the autogenerated API snippets".
- `prefill`: boolean — **"Whether to prefill the API playground with the examples"**.
- `autogenerate`: boolean, default `true` — controls whether code samples are generated at all.

`prefill` is the switch this task needs, and its own description says it draws from "the examples" — i.e. the `example` key already present on the `MiruVersion` schema. No `x-default` is required. (For completeness: `x-default` is a Mintlify extension. On a **security scheme** it prefills unconditionally; on an ordinary schema it is only consulted when `prefill` is on, so it would be redundant here. Mintlify's OpenAPI converter — `dist/openapi/SchemaConverter.js`, `copyExampleIfDefined` in `dist/openapi/utils.js` — carries `example`, `default`, and `x-default` through to page data alike.)

### Blast radius of the global switch — measured, not guessed

`api.examples.prefill` is site-wide. It applies to every OpenAPI-backed page, i.e. all four Platform API versions and all three Device API versions. Counts of `components.parameters` entries carrying a `schema.example`, measured 2026-09-02:

| Spec | parameters | with `schema.example` |
|------|-----------:|----------------------:|
| `docs/references/platform-api/2026-08-17.yaml` | 62 | 60 |
| `docs/references/platform-api/2026-05-06.yaml` | 52 | 50 |
| `docs/references/platform-api/2026-03-09.yaml` | 50 | 47 |
| `docs/references/platform-api/2025-10-21.yaml` | 36 | 17 |
| `docs/references/device-api/v0.2.1/api.yaml` | 3 | 3 |
| `docs/references/device-api/v0.2.0.yaml` | 3 | 3 |
| `docs/references/device-api/v0.1.0.yaml` | 0 | 0 |

Concretely, `config_instance_id` will render as `cfg_inst_123` rather than `{config_instance_id}`, `limit` as `10`, `offset` as `0`, `config_instance_expansions` as `content`. Request bodies with examples will likewise be seeded.

**This is accepted, and is the point of the change rather than a side effect to be minimised.** Stainless authored every one of those examples deliberately; a sample a reader can copy and run beats a sample full of angle brackets. This is the same presentation Stripe and similar API references use. The specs are the single source of the values, so the samples cannot drift from the specs.

Two consequences to keep in mind while reviewing the rendered result:

- The playground's "Send" button will now fire pre-populated requests against real IDs like `cfg_inst_123`. Those return 404, not a mutation of real data, and the reader still has to supply their own API key (`X-API-Key` has no example and is a security scheme with no `x-default`), so no destructive call can be made by accident.
- Examples are now reader-facing defaults rather than illustrative strings. If a future spec pull introduces a misleading example, it becomes visible on the page. That is a reason to review spec pulls, not a reason to keep the placeholders.

### Alternatives considered and rejected

**Redefine `Miru-Version` as an `apiKey` security scheme with `x-default`.** Mintlify prefills security schemes from `x-default` with no config flag, so this would fix only the version header and leave every other placeholder alone. Rejected on three grounds. First, it is a lie about the API: `Miru-Version` is a version selector, not a credential, and modelling it as auth would put it in the docs' authentication UI alongside `X-API-Key` and break the existing `ApiKeyAuth` scheme's presentation. Second, it requires mutating vendored specs (see below). Third, it forgoes the site-wide improvement that is the more valuable half of the outcome.

**Add per-operation `x-codeSamples` with the header hard-coded.** Rejected: it would need one hand-written sample per operation per language across three spec versions (well over a hundred), it fixes the code samples but not the playground field, and Mintlify suppresses autogenerated samples for any operation that has `x-codeSamples`, so every other language would be lost.

**Add `x-default: <version>` to the `MiruVersion` schema.** Rejected as unnecessary: `example` already carries the value and `prefill` already consumes it, and `x-default` on a non-security schema is only honoured when `prefill` is on anyway — so it changes nothing that `prefill` does not already do. It is retained as a fallback in Idempotence and Recovery in case the deployed render disagrees with the schema documentation.

### Why spec edits are avoided

`docs/references/**/*.yaml` are vendored. `api/pull-stainless.sh` downloads `api/device-api.stainless.yaml` and `api/platform-api.stainless.yaml` from Stainless and post-processes them with `api/inject_scopes.py`, `api/add_unix_socket_curl.py`, and `api/generate_event_pages.py`; the result is what gets promoted into `docs/references/`. Plans in `plans/completed/` record that hand edits to these files are overwritten by the next pull. Any spec mutation therefore has to be a script in `api/` wired into `api/pull-stainless.sh`, not a hand edit — which is exactly the cost this plan avoids by using config.

### Prose pages need no change

`docs/developers/platform-api/versioning.mdx` states: "The `Miru-Version` header is required. Requests without the header will be rejected." That remains true and must not be softened. This change makes the docs UI *fill the field in for you*; it does not make the header optional, and nothing in the docs should imply the API supplies a default. No `.mdx` file is edited by this plan.

## Idempotence and Recovery

Every step is safe to repeat. The edit is a single idempotent JSON key — re-applying it is a no-op. All four validation commands are read-only with respect to the working tree. `pnpm install --frozen-lockfile` is idempotent. Nothing is deleted, no spec is mutated, and no pipeline script is touched.

**Rollback:** `git checkout -- docs/docs.json` before committing, or `git revert <sha>` after. The site returns to the current placeholder behaviour immediately on the next deploy; there is no migration and no persisted state.

**Contingency — if the deployed render still shows `<miru-version>` despite `prefill: true`.** This would mean Mintlify's renderer consults `x-default` rather than `schema.example` for header parameters, contradicting the schema's own description.
