A rule's `upload` block declares which registered [bucket](/data-uploads/concepts/buckets) matching files are written to, and the object path within it. 

The `upload` block is optional. If omitted, the rule only manages local retention.

<ParamField path="collection_slug" type="string" required>
  Slug of the [upload collection](/data-uploads/concepts/upload-collections) the resulting uploads are grouped into.

  Example: `robot-logs`
</ParamField>

<ParamField path="bucket" type="string" required>
  Name of the registered bucket this rule uploads to.

  Example: `my-uploads-bucket`
</ParamField>

<ParamField 
  path="path"
  type="string"
  default="{device_id}/{year}-{month}-{day}/{upload_id}/{file_name}"
>
  The template which defines the object path to which the uploaded file is written.

  The following variables are supported, which are filled in when each upload's
  object key is rendered:

  | Variable | Example | Description |
  | --- | --- | --- |
  | `{upload_id}` | `upl_123` | The upload's ID. |
  | `{device_id}` | `dvc_123` | The uploading device's ID. |
  | `{device_name}` | `my-robot` | The device's name. |
  | `{file_name}` | `robot.log` | The source file's basename. |
  | `{year}` | `2026` | The year of the rule's `timestamp`, in its `timezone`. |
  | `{month}` | `01` | The month, zero-padded. |
  | `{day}` | `01` | The day of the month, zero-padded. |
  | `{hour}` | `00` | The hour (24-hour), zero-padded. |
  | `{minute}` | `00` | The minute, zero-padded. |
  | `{timezone}` | `-0500` | The UTC offset of that time, in ISO 8601 basic format (`+0000` in UTC). |
  | `{bundle_id}` | `upl_bdl_123` | The upload's [bundle](/data-uploads/concepts/upload-bundles) ID. Requires `bundle`. |
  | Any [capture](/data-uploads/concepts/file-rules/rule-definition#glob-captures) | `run_42` | The value matched by the capture. |

  <Note>
    By default, time variables are rendered in UTC from Miru's clock when the
    upload is created, just before the agent transfers the file. For example, a
    file written at 23:50 UTC but uploaded at 00:10 UTC gets the next day's date.
    Set [`timestamp`](#param-timestamp) and [`timezone`](#param-timezone) to
    render them from the file's modification time, or in the device's local
    time zone.
  </Note>

  <Warning>
    Templates must contain the `{upload_id}` variable.
  </Warning>
</ParamField>

<ParamField path="timestamp" type="string" default="upload_time">
  The time the path's time variables are rendered from.

  - `upload_time`: when the upload is created, from Miru's clock.
  - `mtime`: the file's last-modified time, from the device's clock.

  <Warning>
    With `mtime`, date folders follow the device's clock. A device whose clock
    is wrong writes to the wrong folders.
  </Warning>
</ParamField>

<ParamField path="timezone" type="string" default="utc">
  The time zone the path's time variables are rendered in.

  - `utc`: Coordinated Universal Time.
  - `device`: the device's local time zone. The agent reads it from its `TZ`
    environment variable or, when `TZ` is unset, from the system time zone
    (`/etc/localtime` on Linux). The offset follows daylight saving time, so
    `{timezone}` changes from `-0500` to `-0400` when it starts.

  The agent runs as a system service, so a `TZ` set in a user's shell doesn't
  reach it. To set it for the agent, add a systemd drop-in:

  ```bash
  sudo systemctl edit miru
  ```

  ```ini
  [Service]
  Environment=TZ=America/New_York
  ```

  Then restart the agent with `sudo systemctl restart miru`.

  Agents that don't report their time zone render `device` rules in UTC.

  For example, a robot in New York that should file each day's recordings
  under its local calendar date:

  ```yaml
  upload:
    path: "{timezone}/{year}-{month}-{day}/{device_name}/{upload_id}/{file_name}"
    timestamp: mtime
    timezone: device
  ```

  A file written at 20:30 EST on January 14 lands under
  `-0500/2026-01-14/...` instead of the next day's folder.
</ParamField>

<ParamField path="bundle" type="string[]">
  A list of unique [captures](/data-uploads/concepts/file-rules/rule-definition#glob-captures) from `source.glob`. 
  
  Uploads from the same
  device and upload collection whose captured values match, *in the listed order*, are
  grouped into a single [bundle](/data-uploads/concepts/upload-bundles).

  <BundleCliVersion />

  Example: `[recording]`
</ParamField>
