On Windows the Miru Agent runs as a Windows service under the virtual account `NT SERVICE\miru-agent`. The account has no password and no administrator rights, and it can only use the folders the installer sets up for it and the folders you grant it.

The agent touches files on your devices in two cases:

- **[Configs](#configs)** — the agent **writes** config instances to disk when it deploys a release.
- **[Data uploads](#data-uploads)** — the agent **reads** files on the device to upload them to your bucket, and deletes them afterwards if the file rule has a `retention` block.

This page explains how Windows permissions apply to the agent, what it can access by default, and how to grant and check access. For Linux devices, see [File system access on Linux](/developers/agent/filesys-access/linux).

<Info>
  Windows is supported in Miru Agent `v0.11.0` and later.
</Info>

## How permissions work

Windows controls file access differently from Linux:

- **Access control lists, not mode bits** — every file and folder has an access control list (ACL) of entries that each allow (or deny) specific rights to an account or group. There are no owner/group/other mode bits.
- **Files inherit from their folder** — an entry set on a folder with the inheritance flags `(OI)` (files) and `(CI)` (subfolders) applies to everything inside it, including files created later. Files rarely carry permissions of their own.
- **No permissions needed on parent folders** — Windows lets accounts open a file by its full path without any access to the folders above it, so there is no equivalent of the Linux execute (`x`) permission on each directory along the path.

So on Windows you grant the agent access **once, on a folder**, and every file in it follows.

<Warning>
  Don't set permissions on individual config files. Each deploy replaces the file with a new one, which takes its permissions from the folder, so permissions set on the old file are lost.
</Warning>

You manage permissions with [`icacls`](https://learn.microsoft.com/windows-server/administration/windows-commands/icacls) from PowerShell opened as administrator. The rights used on this page are:

| Right | Meaning |
|-------|---------|
| `RX` | Read and execute: list a folder, read files |
| `D` | Delete the file or folder |
| `M` | Modify: read, write, create, and delete |
| `F` | Full control, including changing permissions |
| `(OI)(CI)` | Apply the entry to files and subfolders inside the folder |

## Default access

The installer creates the following folders. They don't inherit permissions from `%ProgramData%`, and Local System and Administrators have full control of them.

| Path | Purpose | Agent access | Other access |
|------|---------|--------------|--------------|
| `%ProgramData%\Miru` | Agent state, credentials, device identity | Read and write | None |
| `%ProgramData%\Miru\logs` | Log files (hourly rotation) | Read and write | None |
| `%ProgramData%\Miru\configs` | Deployed config instance files | Read and write | `Miru Agent Users` can read |
| `%ProgramData%\Miru\device-api` | [Device API](/developers/device-api/authn) discovery file | Read and write | `Miru Agent Users` can read |

The agent has full control of the files and folders it creates inside these folders, but it cannot delete the installer-created folders or change their permissions. Each one contains an `installer-sentinel` folder that only Local System and Administrators can access, so the agent can never empty it. Upgrading or repairing the agent reapplies these permissions.

Outside these folders, the agent only has what a folder already allows broad groups such as `Users` and `Authenticated Users`. That is often write access for folders created at the root of `C:\`, and no access under `C:\Windows` or `C:\Program Files`. Don't rely on it: grant the agent access explicitly, as described below.

## Configs

### Default config folder

Deploying to any path inside `%ProgramData%\Miru\configs` works out of the box, for example `C:\ProgramData\Miru\configs\mobility.json`. Config file paths on Windows must be absolute and start with a drive letter.

Members of the local `Miru Agent Users` group can read the deployed files. See [Reading configs from your application](#reading-configs-from-your-application).

### Custom config folders

To deploy to a folder outside `%ProgramData%\Miru\configs`, grant the agent **modify** (`M`) access to the folder that holds the config files. A deploy needs to:

1. Copy the current file to a `miru.backup.*` file next to it, so a failed deploy can be rolled back.
2. Write the new contents to a temporary folder next to the file and move it into place, so readers never see a partial file.
3. Delete the backup once every config instance in the deployment is written.

For example, to deploy to `C:\robot\configs\mobility.json`:

```powershell PowerShell
icacls "C:\robot\configs" /grant "NT SERVICE\miru-agent:(OI)(CI)M"
```

If the folder doesn't exist yet, the agent creates it, which requires permission to create folders in the nearest folder that does exist. Create the folder yourself and grant access on it instead, so the agent's access stays limited to that folder.

If the agent can't write to a folder, the deployment fails with an access-denied error and the existing file is left unchanged.

### Locking down a custom folder

A new folder created at the root of `C:\` inherits modify access for every signed-in user, so any local account could change your configs. To restrict a custom config folder, replace its inherited permissions so that only Local System and Administrators can change it, members of `Miru Agent Users` can read it, and the agent can modify it:

```powershell PowerShell
foreach ($dir in "C:\robot", "C:\robot\configs") {
    New-Item -ItemType Directory -Force $dir | Out-Null
    icacls $dir /inheritance:r /grant:r "*S-1-5-18:(OI)(CI)F" "*S-1-5-32-544:(OI)(CI)F" "Miru Agent Users:(OI)(CI)RX"
}
icacls "C:\robot\configs" /grant "NT SERVICE\miru-agent:(OI)(CI)M"
```

- `/inheritance:r` removes the permissions inherited from the parent folder.
- `*S-1-5-18` is Local System and `*S-1-5-32-544` is the built-in Administrators group; `icacls` accepts these well-known security identifiers on any Windows language.
- The parent folder is locked down too, so other accounts can't rename or replace the config folder.

<Note>
  If a folder already existed, check that Local System or Administrators owns it before relying on these permissions, since a folder's owner can always change them:

  ```powershell PowerShell
  (Get-Acl "C:\robot\configs").Owner
  ```
</Note>

### Reading configs from your application

Applications read deployed configs with the permissions of the account they run as. Add that account to the local `Miru Agent Users` group, which can read `%ProgramData%\Miru\configs` and any custom folder locked down as shown above:

```powershell PowerShell
# A user account
Add-LocalGroupMember -Group "Miru Agent Users" -Member "robot-operator"

# A Windows service's account
Add-LocalGroupMember -Group "Miru Agent Users" -Member "NT SERVICE\RobotApp"
```

Membership takes effect the next time the user signs in, or the next time the application's service starts. Remove access with `Remove-LocalGroupMember`. The same group grants access to the [Device API](/developers/device-api/authn).

<Warning>
  Don't add broad groups such as `Users`, `Authenticated Users`, or `Everyone` to `Miru Agent Users`, or grant them access to config folders. Configs may hold secrets, and group members can also call every Device API endpoint.
</Warning>

## Data uploads

To upload data, the agent lists the folder a [file rule's](/data-uploads/concepts/file-rules/overview) `source.glob` matches in and reads the matched files. Grant the agent **read and execute** (`RX`) access on that folder; files inside it inherit the access:

```powershell PowerShell
icacls "D:\robot\logs" /grant "NT SERVICE\miru-agent:(OI)(CI)RX"
```

Uploads are read-only. The agent does not need write access to the source files.

### Deleting local files

If a file rule has a [`retention`](/data-uploads/concepts/file-rules/rule-definition#retention) block, the agent deletes each matching file once its retention guarantee ends. Grant **delete** (`D`) as well:

```powershell PowerShell
icacls "D:\robot\logs" /grant "NT SERVICE\miru-agent:(OI)(CI)(RX,D)"
```

For a glob that matches files in subfolders, such as `D:\robot\logs\**\*.log`, the `(CI)` flag carries the access into every subfolder.

## Checking access

List a folder's permissions with `icacls`:

```powershell PowerShell
icacls "C:\robot\configs"
```

The output lists one entry per account. For the locked-down config folder above, it looks similar to:

```text
C:\robot\configs NT SERVICE\miru-agent:(OI)(CI)(M)
                 NT AUTHORITY\SYSTEM:(OI)(CI)(F)
                 BUILTIN\Administrators:(OI)(CI)(F)
                 ROBOT-PC\Miru Agent Users:(OI)(CI)(RX)
```

Look for the `NT SERVICE\miru-agent` entry and its rights. An `(I)` in an entry means it is inherited from the parent folder rather than set on this folder. Subfolders or files whose inheritance was turned off don't receive the folder's entries, so check those separately.

## Removing access

To remove every entry for the agent from a folder:

```powershell PowerShell
icacls "C:\robot\configs" /remove "NT SERVICE\miru-agent"
```

## Granting access before installing

The `NT SERVICE\miru-agent` account name only resolves once the agent is installed. To grant access earlier, for example in a machine image, use the service's security identifier instead. `sc.exe` prints it at any time, including before installation:

```powershell PowerShell
sc.exe showsid miru-agent
```

Pass the SID to `icacls` with a `*` prefix:

```powershell PowerShell
icacls "C:\robot\configs" /grant "*<SID>:(OI)(CI)M"
```

<Note>
  Drive letters mapped to network shares belong to a user's sign-in session, so the agent's service can't see them. Use local paths for config folders and upload sources.
</Note>
