---
title: "Archive format"
---

Every backup is a single zip archive. The format is a public contract: each resource in
it is a [Platform API](/developers/platform-api/overview) resource, so the Platform API
reference documents every field.

## Location

Archives are written under the backup prefix, `miru-backup/` by default, one per successful run:

```
miru-backup/
├── .miru/
│   └── probe/
├── miru-backup-20261101T030000Z.zip
└── miru-backup-20261102T030000Z.zip
```

Each archive is named `miru-backup-<timestamp>.zip`, where the timestamp is the run's
`snapshot_at` in UTC. Archive names sort in time order, so the newest archive is the last
one by name.

Archive names don't include the workspace. If more than one workspace backs up to the same
bucket, give each workspace its own prefix. The manifest's `workspace_id` says which
workspace an archive came from.

`.miru/probe/` holds the empty objects Miru writes to
[check the bucket](/admin/backups/set-up#turn-on-backups) each time the backup settings are
saved. They aren't archives, and you can delete them.

## Contents

```
miru-backup-20261102T030000Z.zip
├── README.md
├── content/
│   ├── calibrations/
│   │   └── cal_123
│   └── config_instances/
│       └── cfg_inst_123
├── resources/
│   ├── api_keys.jsonl
│   ├── calibrations.jsonl
│   ├── config_instances.jsonl
│   ├── config_schema_git_commits.jsonl
│   ├── config_schemas.jsonl
│   ├── config_types.jsonl
│   ├── deployments.jsonl
│   ├── devices.jsonl
│   ├── git_commits.jsonl
│   ├── groups.jsonl
│   ├── releases.jsonl
│   └── users.jsonl
└── manifest.json
```

- `README.md` lists the resource types in the archive, explains how to read it and links
  back to these docs.
- `resources/` holds one file per resource type. See [resources](#resources).
- `content/` holds the stored content of each config instance and calibration. See
  [content](#content).
- `manifest.json` describes the archive and lists a checksum for every other file. See
  [manifest](#manifest).

Every resource type has a file, even when the workspace has none of that type. An empty
file means the workspace had no resources of that type.

## Resources

Each file in `resources/` is [JSON Lines](https://jsonlines.org): one Platform API
resource per line. Resources use the Platform API version named in the manifest's
`platform_api_version`.

| File | Resource | Expansions |
| ---- | -------- | ---------- |
| `api_keys.jsonl` | API key | |
| `calibrations.jsonl` | Calibration | |
| `config_instances.jsonl` | Config instance | |
| `config_schema_git_commits.jsonl` | Config schema git commit | |
| `config_schemas.jsonl` | Config schema | `documents` |
| `config_types.jsonl` | Config type | |
| `deployments.jsonl` | Deployment | `config_instances` |
| `devices.jsonl` | Device | |
| `git_commits.jsonl` | Git commit | |
| `groups.jsonl` | Group | |
| `releases.jsonl` | Release | `config_schemas` |
| `users.jsonl` | User | |

Expansions are included as the [expansions](/developers/platform-api/query-params/expansions)
query parameter would return them. They hold the schema documents, which config instances
each deployment contains and which config schemas each release contains.

`config_schema_git_commits.jsonl` links each config schema to the git commits it was pushed
from, with the schema's file paths in each commit. It has its own file because the
`config_schema_git_commits` expansion on config schemas returns only one page.

Archived devices, releases and config types are included, with `archived_at` set. Deleted
API keys are included, with `deleted_at` set. API keys never include their secret.

## Content

Each file in `content/` holds the stored content of one config instance or calibration,
named by the resource's ID: `content/config_instances/<id>` and
`content/calibrations/<id>`. The bytes are exactly as they were stored, with no
re-encoding. The manifest lists every content file with its checksum.

## Manifest

Miru uploads each archive whole, so any archive in your bucket is complete. `manifest.json`
describes it.

```json
{
  "format_version": "1.1",
  "platform_api_version": "2026-11-04.everglades",
  "workspace_id": "wsp_123",
  "snapshot_at": "2026-11-02T03:00:00Z",
  "resource_counts": {
    "api_keys": 3,
    "calibrations": 64,
    "config_instances": 812,
    "devices": 112,
    "releases": 38,
    "users": 9
  },
  "files": [
    {
      "path": "README.md",
      "size": 612,
      "sha256": "9f2c..."
    },
    {
      "path": "resources/calibrations.jsonl",
      "size": 48211,
      "sha256": "41ab..."
    }
  ]
}
```

<ParamField path="format_version" type="string">
  The version of the archive format, as `major.minor`. See [versioning](#versioning).

  Example: `1.1`
</ParamField>

<ParamField path="platform_api_version" type="string">
  The [Platform API version](/developers/platform-api/versioning) of every resource in
  the archive.

  Example: `2026-11-04.everglades`
</ParamField>

<ParamField path="workspace_id" type="string">
  The ID of the workspace the archive was taken from.

  Example: `wsp_123`
</ParamField>

<ParamField path="snapshot_at" type="timestamp">
  The point in time the archive captures. Every resource is as it was at this moment.

  Example: `2026-11-02T03:00:00Z`
</ParamField>

## Versioning

`format_version` covers the archive layout and the manifest. The resources inside follow
their own [Platform API version](/developers/platform-api/versioning), named in
`platform_api_version`.

- **Minor versions** only add: new fields in the manifest or new resource types in
  `resources/`. A reader written for `1.0` can read any `1.x` archive.
- **Major versions** may remove or change things. Each major version is announced in the
  [changelog](/changelog/product) before it ships.

Archives are never rewritten, so an archive always matches the format version in its
manifest.
