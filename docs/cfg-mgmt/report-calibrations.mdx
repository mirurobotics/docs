This guide details how to report [calibrations](/cfg-mgmt/concepts/calibrations) through the Miru Agent's [Device API](/developers/device-api/overview).

## Overview

<CalibrationDef />

Miru allows on-device applications to report calibrations using the <DeviceApiLink endpoint="calibrations/create">create calibration</DeviceApiLink> endpoint in the Device API.

When a calibration is reported, the agent saves it on the device and immediately returns a `200` response, regardless of whether the device is online or offline. Once a device is online, the agent uploads the calibration to Miru.

## Prerequisites

To follow this guide, you must have:

- A device installed with a Miru Agent [v0.12.0](/changelog/agent#v0-12-0) or later

To provision a device, see [Provision a device](/provision-devices) guide.

## Components

A [component](/cfg-mgmt/concepts/components) is a kind of hardware that devices report calibrations for, such as an arm, a camera, or a Robotiq 2F-85. A calibration names its component with a [slug](/cfg-mgmt/concepts/components#param-slug), such as `kuka-arm`, `realsense-d435`, or `robotiq-2f-85`. 

When a calibration is reported, Miru checks if its component exists and creates it if it doesn't.

### Roles

Oftentimes devices have multiple units of the same component, such as multiple arms. In this case, a [role](/cfg-mgmt/concepts/components#param-roles) distinguishes the units.

A device with two arms might distinguish them as `left` and `right`.

### Aspects

Separately, some components are calibrated in multiple ways. For example, a RealSense D435 might report `intrinsics` and `extrinsics`.

An [aspect](/cfg-mgmt/concepts/components#param-aspects) distinguishes parts of a unit that are calibrated separately.

Both are optional. A device with one arm, calibrated one way, reports only the component. The device keeps a separate history for each component, role, and aspect, and Miru creates a role or aspect the first time a calibration reports it.
 
## Send a calibration

Send a `POST` request to `/calibrations`.

### Required

<ParamField body="component" type="string" required>
  The [slug](/cfg-mgmt/concepts/components#param-slug) of the calibrated component.

  Example: `kuka-arm`
</ParamField>

<ParamField body="content.format" type="enum" required>
  The file format of `content.data`: `json`, `yaml`, `jsonc`, `xml` or `text`.
</ParamField>

<ParamField body="content.data" type="string" required>
  The calibration result, usually the full text of the calibration file. At most 1 MiB.
</ParamField>

### Optional

Set a role when the device has more than one unit of the component, and an aspect when a unit is calibrated more than one way. A device with one arm, calibrated one way, sends the component and the content.

<ParamField body="role" type="string">
  The slug of the unit's [role](/cfg-mgmt/concepts/components#param-roles).

  Example: `front-left`
</ParamField>

<ParamField body="aspect" type="string">
  The slug of the calibrated [aspect](/cfg-mgmt/concepts/components#param-aspects).

  Example: `pose`
</ParamField>

<ParamField body="serial_number" type="string">
  The serial number of the calibrated unit. At most 255 characters.

  Example: `SN-1234`
</ParamField>

### Example

These examples report the pose of the `kuka-arm` unit `front-left` from the file `kuka-arm-pose.json`.

<Tabs>
  <Tab title="Linux">
    [jq](https://jqlang.org/) escapes the file's content as a JSON string.

    ```bash wrap
    jq -n --rawfile data kuka-arm-pose.json \
      '{component: "kuka-arm", role: "front-left", aspect: "pose", serial_number: "SN-1234", content: {format: "json", data: $data}}' |
    curl --unix-socket /run/miru/miru.sock \
      --request POST \
      --url http://localhost/v0.2/calibrations \
      --header 'Content-Type: application/json' \
      --data-binary @-
    ```
  </Tab>
  <Tab title="Windows">
    ```powershell wrap
    $api = Get-Content -Raw "$env:ProgramData\Miru\device-api\device-api.json" | ConvertFrom-Json
    $body = @{
      component      = "kuka-arm"
      role           = "front-left"
      aspect         = "pose"
      serial_number  = "SN-1234"
      content        = @{ format = "json"; data = (Get-Content -Raw "kuka-arm-pose.json") }
    } | ConvertTo-Json -Depth 3
    Invoke-RestMethod -Method Post `
      -Uri "http://127.0.0.1:$($api.port)/v0.2/calibrations" `
      -Headers @{ Authorization = "Bearer $($api.token)" } `
      -ContentType "application/json" `
      -Body $body
    ```
  </Tab>

## Response

The agent saves the calibration on the device, then responds with `200 OK`, a new report ID and the time it received the calibration:

```json nocopy
{
  "report_id": "0f8e7c2a-5b1d-4c3e-9a6f-2d4b8e1c7a90",
  "reported_at": "2026-03-10T12:00:00Z"
}
```

The agent responds the same way while the device is offline, and uploads the calibration once Miru is reachable. Miru records each report ID once, so the agent's own upload retries never record a calibration twice. Each request gets a new report ID, though, so don't resend one that got a `200`.

## Errors

On an error the agent saves nothing, so the request is safe to retry once the cause is fixed. A request that times out may have been saved, and resending it may record it twice.

| Status | Code | Cause |
| ------ | ---- | ----- |
| `401` | | Windows only: the bearer token is missing or stale. Re-read it as described in [Authentication](/developers/device-api/authn). |
| `413` | `calibration_too_large` | `content.data` is over 1 MiB. |
| `422` | [PLACEHOLDER: error code] | The request is malformed, such as a missing field or an unknown format. |
| `507` | `calibration_buffer_full` | 1,000 calibrations are waiting to upload, usually because the device has been offline a long time. Retry later. |

## Dropped calibrations

The agent drops a calibration and logs an error when:

- Miru rejects it: a slug or serial number is invalid, the content doesn't parse as its format, or it would pass a [component limit](/cfg-mgmt/concepts/components#create-a-component).
- Its upload keeps failing for about a day, for reasons other than the device being offline.
- It still hasn't uploaded 90 days after it was reported, for example because the device has been offline that long.

The agent only checks a request's shape and size, so a `200` doesn't rule these out. To confirm a calibration reached Miru, find it on the device's **Calibrations** tab or check the [agent logs](/developers/agent/commands#logs).
