When a calibration routine finishes on a device, your software sends the result to the [Miru Agent](/developers/agent/overview) through the [Device API](/developers/device-api/overview). The agent saves it on the device right away and uploads it to Miru whenever Miru is reachable, so a calibration survives network outages and agent restarts.

## How it works

<Frame>
  [PLACEHOLDER: diagram of the calibration flow: a calibration routine on the device, the Device API request to the Miru Agent, the agent's on-device buffer, and the upload to Miru]
</Frame>

1. A calibration routine runs on the device and produces a result, such as a JSON or YAML file.
2. Your software [reports the calibration](/cfg-mgmt/report-calibrations) to the Miru Agent with the Device API.
3. The agent saves the calibration on the device and responds immediately, without waiting for Miru.
4. The agent uploads saved calibrations to Miru in the order it received them, retrying until Miru is reachable.
5. Miru records the calibration under its [component](/cfg-mgmt/concepts/components), role and aspect.

## Recorded, never deployed

Miru only records calibrations. It never sends them back to a device, and they are never part of a [release](/concepts/releases) or a [deployment](/concepts/deployments/overview). Deployments carry what the cloud sends to a device, while calibrations record what the device reports.

Calibration files stay where your software writes them on the device. The agent doesn't read calibration files from disk or write them. It only uploads what your software sends it.

Calibrations are meant for results produced on the robot. Values produced off the robot, such as numbers from a setup station or entered by hand, are ordinary device configuration. Manage them as [config instances](/cfg-mgmt/concepts/config-instances) and deploy them like any other config.

## Properties

<ParamField path="device" type="Device">
  <ImmutableBadge />

  The [device](/concepts/devices/overview) that reported the calibration.
</ParamField>

<ParamField path="component" type="Component">
  <ImmutableBadge />

  The [component](/cfg-mgmt/concepts/components) the calibrated unit belongs to.
</ParamField>

<ParamField path="role" type="Role">
  <ImmutableBadge /> <NullableBadge />

  The [role](/cfg-mgmt/concepts/components#roles-and-aspects) the calibrated unit fills on the device. Null if the device reported no role.
</ParamField>

<ParamField path="aspect" type="Aspect">
  <ImmutableBadge /> <NullableBadge />

  The [aspect](/cfg-mgmt/concepts/components#roles-and-aspects) of the unit that was calibrated. Null if the device reported no aspect.
</ParamField>

<ParamField path="serial_number" type="string">
  <ImmutableBadge /> <NullableBadge />

  The serial number of the physical unit that was calibrated, not of the device. Free text, at most 255 characters. Null if the device reported none.

  Example: `M500-1234`
</ParamField>

<ParamField path="content" type="object">
  <ImmutableBadge />

  The calibration result, stored exactly as the device reported it. Content has a `format` and the `data` serialized in that format, at most 1 MiB.

  Allowed formats:
  - `json`
  - `yaml`
  - `jsonc`
  - `xml`
  - `text`

  Miru checks that `json`, `jsonc` and `yaml` content parses, and stores `xml` and `text` content as given.
</ParamField>

<ParamField path="deployment" type="Deployment">
  <ImmutableBadge /> <NullableBadge />

  The [deployment](/concepts/deployments/overview) the device was on when it reported the calibration. Null if the device had no deployment, or if the deployment was later deleted.
</ParamField>

<ParamField path="reported_at" type="datetime">
  <ImmutableBadge />

  Timestamp of when the Miru Agent on the device received the calibration.

  The agent may upload a calibration long after it was reported, for example after a network outage, so `reported_at` can be well before Miru records the calibration. Calibration history is ordered by `reported_at`.
</ParamField>

## History

Calibrations are append-only. Miru never changes or deletes a calibration, and no user can create, edit or delete one. A calibration is only removed when the device that reported it is deleted.

Each device keeps a separate history for every combination of component, role and aspect it reports. The newest calibration in a history, by `reported_at`, is that unit's current calibration.

## Duplicates

Every report creates a new calibration, even if its content matches an earlier one. Sending the same calibration twice records it twice.

On rare occasions, Miru may also record a calibration twice without it being sent twice. If the agent uploads a calibration but loses Miru's response, for example because of a timeout or an agent restart, it uploads the calibration again.

## Access

Users can view the calibrations of devices in the [groups](/concepts/groups/overview) they can view. Only a device can create a calibration, and only for itself.
